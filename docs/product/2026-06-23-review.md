# Product Review — whole product — 2026-06-23

> Method: codebase + docs (no `--live`; flows reasoned from source, not a running app) ·
> Persona: see persona.md · Use cases: see use-cases.md

## Summary
Splashdown serves its two co-primary personas well on their *primary* jobs: the
one-command `init` (UC3), the per-checkout auto-named sims with auto-recreate-on-Xcode-bump
(UC2/UC4), and `doctor`'s port-wiring autofix (UC5) are genuinely strong and, in the mobile
case, solve a pain nothing else does. The weak spots are at the **edges of the happy path**:
the first thing a curious user might do (`splash` before `init`) dumps a traceback, a
`set`-resource error tells them to run a command that doesn't exist, an unconfirmed
`destroy` can delete a sim, and — most strategically — a teammate cloning a configured repo
isn't wired up automatically. The single most important change depends on direction: if team
adoption is the wedge, **make a fresh clone self-wire (UC6)**; if not, **fix the broken
first-run error messages (C1, H2)** first.

## What works well
- **One-command onboarding (UC3)** — `init` scans, scaffolds, wires the loader *and* the
  post-checkout hook, runs wiring checks, and does the first sync. Time-to-first-value is one
  command; the printed ports give immediate proof it worked.
- **Auto-recreate "latest" sims + `prune` (UC4)** — the distinctive feature. Reconciling stale
  sims on `run` and clearing the Xcode template pile is exactly the mobile persona's recurring
  pain, and nothing in the standard toolchain does it.
- **`doctor` closes the env-var-vs-hardcoded-port gap (UC5)** — proactively detects and (where
  safe) patches the config files that would otherwise silently ignore the allocated port.
- **Machine-wide registry + live `bind()` probes (UC1)** — coordination across *unrelated*
  repos, not just worktrees, is the right scope for the real problem.
- **Discoverability despite a big surface** — the custom tiered `--help` epilog
  (`_EpilogOnlyFormatter`, `cli.py:31`) curates ~15 subcommands into readable tiers.
- **Respects existing setups** — hook-manager coexistence (lefthook/husky) and the
  no-loader fallback (deliver to `.env`/`.env.local`, else print instructions) avoid hijacking.
- **`prune` is the model for safe destructive ops** — `--dry-run` + a `[y/N]` confirm + `--yes`.

## Findings

### Critical
- **`set`-resource error points to a command that doesn't exist** (UC1/UC3, effort S) —
  `provisioning.py:81` tells the user to run `mise run set NAME=VALUE`, but the real command is
  `splash env set NAME=VALUE`. A user blocked on an unfilled `set` resource follows a dead-end
  instruction and can't discover the right path from the message. Fix the message to name
  `splash env set` (and/or a `default = ...`).

### High
- **A fresh clone doesn't wire itself; the teammate must re-`init`** (UC6, effort M) — git
  doesn't install hooks on clone, and the registry/env are per-machine, so a teammate who
  clones a repo with a committed `splashdown.toml` gets nothing until they run `splash init` —
  which *re-scans and re-scaffolds*, the wrong mental model for an already-configured repo.
  There's no lightweight "wire me up" verb. Add `splash install` (install hook + first sync,
  no scaffolding), or make `init` detect an existing recipe and just wire+sync.
  **This is Critical if team adoption is the chosen wedge.**
- **Running `splash` before `init` prints a Python traceback** (UC3, effort S) — `main()`
  catches only `DeviceError`/`ValueError` (`cli.py:~417`), so the `FileNotFoundError` from
  `provision()` (`provisioning.py:35`, "no splashdown.toml found") escapes as a raw stack
  trace. A curious new user's first command fails ugly. Catch it and print
  `no splashdown.toml here — run \`splash init\`` (the `--rescan` path already does this at
  `commands.py:1336`; the sync path should too).
- **`splash destroy` deletes a sim with no confirmation** (UC2/UC4, effort S) — `cmd_destroy`
  removes the sim/emulator + registry entry immediately, while the *less* destructive `prune`
  confirms. Inconsistent and risky (`splash destroy simulator default` is unrecoverable). Add a
  confirm + `--yes` to match `prune`.
- **React-Native-on-Android Metro port isn't wired** (UC5, effort L) — the README's own "Known
  limitation": `gradle assembleDebug` may default to 8081, so for an RN/Android dev the "ports
  just work" promise has a hole on one of the two platforms they ship. At minimum surface this
  loudly in `doctor` output for RN projects; track the missing check as a roadmap item.

### Medium
- **Cleanup is fragmented across four verbs** (UC7, effort M) — `gc`, `target refresh`,
  `target prune`, and `env release` all "clean up" different things, and users can't infer
  which to reach for (the `status --check` summary has to route them explicitly). Cross-link
  them in help/status, or consolidate under one `clean`-style entry point with subscopes.
- **`--force` means two unrelated things** (UC1 vs UC3, effort S) — `sync --force` reallocates
  resources; `init --force` overwrites the recipe file. Same flag, different blast radius.
  Consider distinct names (e.g. `init --overwrite`).
- **`env set`/`release` can't target another checkout, but `env get` can** (UC8, effort S) —
  `--checkout` exists on `env get` only. Either add it to `set`/`release` or document the
  asymmetry; right now it reads as an inconsistency.
- **Positional type/variant inference can make a variant unreachable** (UC2, effort M) —
  `run/start/stop/destroy` drop argparse `choices` so a lone token can be a type *or* a variant;
  a variant named `device`/`simulator`/`emulator` loses to the type name, and `splash run X` is
  resolved heuristically. At least error clearly on the ambiguous case instead of silently
  picking.
- **No machine-wide view of allocations** (UC8, effort M) — `status` is per-checkout; a
  worktree-heavy user has no way to see everything reserved across all repos without reading the
  TSV by hand. A `splash status --global` (or `splash ls`) would serve the coordination story
  the registry already enables.

### Suggestions
- **First-value hint after `init`** (effort S) — print the exact next step at the point of need
  (e.g. for direnv, "run `direnv allow`"). Verify whether `init` already does this for each
  loader; if not, add it.
- **Make `splash env set` discoverable from `status`** (effort S) — when a `set` resource is
  unfilled, `status` could show the exact `splash env set` line to run.
- **Port-stability trust is now correct (no action)** — the bug where a checkout's own running
  dev server could get its port reallocated was fixed on 2026-06-23; UC1 now behaves as the
  persona expects. Noted so it isn't re-raised.

## Prioritized recommendations
1. **Fix the `set`-resource error message** (C1) — name `splash env set`; removes a dead-end that
   blocks provisioning for set-type resources. Critical / S.
2. **Catch `FileNotFoundError` in `main()`** (H2) — turn the pre-`init` traceback into a one-line
   "run `splash init`." Protects every new user's first impression. High / S.
3. **Confirm `splash destroy`** (H3) — match `prune`'s `[y/N]` + `--yes`; closes an unconfirmed
   irreversible delete. High / S.
   <br>*(Then, once direction is set:)* **`splash install` for fresh clones** (H1) — the top
   lever if team adoption is the wedge. M.
