## GH-01 — argument-level probe: the three event values each adapter delivers

Run against the configuration `splash init` itself wrote in the GH-02 to GH-07 repositories, with
a recording stub named `splash` placed first on `PATH` and outside every repository. The stub
appended its argv on each invocation. `git checkout` between two branches at the same commit
yields `old == new`; `git worktree add` yields the null object id as `old`.

Observed argv, as `hook post-checkout <old> <new> <flag>`. Every invocation received exactly five
argv entries — `hook`, `post-checkout`, and the three event values:

| Adapter | `git checkout feature` | `git checkout main` | `git worktree add` |
| --- | --- | --- | --- |
| native Git | `36a7ead7…` `36a7ead7…` `1` | `36a7ead7…` `36a7ead7…` `1` | `0000000000000000000000000000000000000000` `36a7ead7…` `1` |
| lefthook | `3100ee8d…` `3100ee8d…` `1` | `3100ee8d…` `3100ee8d…` `1` | `0000000000000000000000000000000000000000` `3100ee8d…` `1` |
| pre-commit | `fc9bc751…` `fc9bc751…` `1` | `fc9bc751…` `fc9bc751…` `1` | `0000000000000000000000000000000000000000` `fc9bc751…` `1` |
| prek (`prek.toml`) | `3d2df665…` `3d2df665…` `1` | `3d2df665…` `3d2df665…` `1` | `0000000000000000000000000000000000000000` `3d2df665…` `1` |
| simple-git-hooks | `03405086…` `03405086…` `1` | `03405086…` `03405086…` `1` | `0000000000000000000000000000000000000000` `03405086…` `1` |
| husky | `c44ea614…` `c44ea614…` `1` | `c44ea614…` `c44ea614…` `1` | `0000000000000000000000000000000000000000` `c44ea614…` `1` |

`$PWD` was the checkout the event belonged to in every row — the linked worktree for the
worktree-creation column, the primary checkout otherwise.

The two environment-mapped adapters were then driven over a branch switch between different
commits and over a file checkout, which is where an incorrect mapping would show:

| Adapter | Event | Observed `<old> <new> <flag>` |
| --- | --- | --- |
| pre-commit | `git checkout main` from `feature` at `a9e80774…`, main at `fc9bc751…` | `a9e80774…` `fc9bc751…` `1` |
| pre-commit | `git checkout feature -- vite.config.js` | `fc9bc751…` `fc9bc751…` `0` |
| prek | `git checkout main` from `feature` at `634a7240…`, main at `3d2df665…` | `634a7240…` `3d2df665…` `1` |
| prek | `git checkout feature -- vite.config.js` | `3d2df665…` `3d2df665…` `0` |

So for both tools `PRE_COMMIT_FROM_REF` is Git's first argument (the previous HEAD),
`PRE_COMMIT_TO_REF` is its second (the new HEAD), and `PRE_COMMIT_CHECKOUT_TYPE` carries the
branch flag verbatim, including `0`. That matches https://pre-commit.com/#post-checkout.

prek's published contract
(https://prek.j178.dev/reference/environment-variables/#variables-exposed-to-hooks) lists
`PRE_COMMIT_CHECKOUT_TYPE` as "The checkout flag supplied to `post-checkout`" and
`PRE_COMMIT_FROM_REF`/`PRE_COMMIT_TO_REF` as the starting and destination refs; the observed
values above match.

## GH-08 — simple-git-hooks forwarding contract, from source

Read from `node_modules/simple-git-hooks/simple-git-hooks.js` at 2.14.0:

- `_setHook` writes `PREPEND_SCRIPT + command` into the hook file and chmods it `0o755`. The
  configured command is copied in verbatim with no argument rewriting, so the hook script's own
  positional parameters are Git's three arguments and `"$1" "$2" "$3"` is the correct forwarding
  form. The runtime probe in GH-01 confirms this.
- `PREPEND_SCRIPT` is only `#!/bin/sh`, a `SKIP_SIMPLE_GIT_HOOKS` guard, and an optional
  `SIMPLE_GIT_HOOKS_RC` source.
- `_getHooksDirPath` honors `git config --local core.hooksPath` and otherwise writes into the
  Git common directory's `hooks`.
- `_getConfig` reads, in order: `.simple-git-hooks.cjs`, `.simple-git-hooks.js`,
  `.simple-git-hooks.mjs`, `simple-git-hooks.cjs`, `simple-git-hooks.js`,
  `simple-git-hooks.mjs`, `.simple-git-hooks.json`, `simple-git-hooks.json`, then the
  `simple-git-hooks` key in `package.json`. The package.json key is spelled
  `simple-git-hooks`, not `simpleGitHooks`, and a string value there is a path to another
  config file rather than a hook table.
- `setHooksFromConfig` deletes every valid hook absent from the configuration unless
  `preserveUnused` lists it. A native `.git/hooks/post-checkout` in a simple-git-hooks project
  is therefore removed on the next run, which is why splashdown writes into the manager's own
  configuration instead.

Splashdown writes to the first editable file in that same order and never executes or edits the
dynamic JavaScript shapes.

## Not verified

- **Overcommit.** The gem could not be installed in this sandbox, so its recognition path was
  exercised only through `.overcommit.yml` presence, and its installed-hook signature
  (`overcommit` appearing in a generated hook) is inferred from its published behavior rather
  than observed. Splashdown writes nothing for Overcommit, so the untested surface is detection
  and the wording of the manual instruction, not an adapter.
- **husky inside a linked worktree.** Observed during GH-01: husky sets
  `core.hooksPath = .husky/_`, which is a worktree-relative path, and `.husky/_` is gitignored.
  A `git checkout` performed *inside* a freshly created linked worktree produced no hook
  invocation at all, while `git worktree add` run from the primary checkout did fire. This is
  husky's behavior, not splashdown's, and it is why splashdown reports husky as configured but
  inactive until the project's own husky install has run in that checkout. Documented in
  `docs/features/init-and-onboarding.md`.
- **direnv and devbox.** Loaders rather than hook managers; out of scope for this family.

### What the original run could not see

The `Repeat splash init --overwrite → no diff` column in GH-02 to GH-07 is an idempotency check,
not a fidelity check. Both editors are idempotent no matter what the first write did, so that
column is byte-identical whether or not the first init destroyed the file. Every added scenario
below therefore records the **first** init's diff.

### GH-10 — pre-commit configuration with only remote repos

The arrangement of any project that has never had a `local` repo, which is the common case.
`.pre-commit-config.yaml` carried one `pre-commit-hooks` remote entry.

| Step | Observed |
| --- | --- |
| `splash init` | `wired post-checkout in .pre-commit-config.yaml (pre-commit)` |
| First-init diff | the remote entry untouched; a `- repo: local` block appended with `hooks:` at column 4 and the hook item at column 6 |
| Real `pre-commit run --hook-stage post-checkout --all-files` | `splashdown post-checkout … Passed` |
| Repeat `splash init --overwrite` | no diff |
| `splash trust` | `.git/hooks/post-checkout` generated by pre-commit |
| `git checkout -b feature`, `git checkout main`, `git worktree add` | hook ran on each |
| Ports | primary `WEB_DEV_PORT=5174`, worktree `WEB_DEV_PORT=5175` |

to, which is a YAML scanner error (`mapping values are not allowed here`). `pre_commit_state` then
still answered `ok`, so `splash doctor` reported a green `hook ✓` for a file pre-commit cannot

runs the same structural analysis and answers `unrecognized` for a document it cannot read.

### GH-11 — a prek project configured in `.pre-commit-config.yaml` with no `prek.toml`

`prek install --hook-type post-checkout` was run first, so the installed hook's
`# File generated by prek` signature resolves detection to prek. The repository's only
configuration was `.pre-commit-config.yaml` with a `lint-canary` hook.

| Step | Observed |
| --- | --- |
| `splash init` | `wired post-checkout in .pre-commit-config.yaml (prek)` |
| `prek.toml` afterwards | **not created** |
| Real `prek run --hook-stage post-checkout --all-files` | `lint-canary … Passed`, `splashdown post-checkout … Passed` |
| Repeat `splash init --overwrite` | no diff |
| `git checkout` ×2 and `git worktree add` | both hooks ran on each |
| Ports | primary `WEB_DEV_PORT=5176`, worktree `WEB_DEV_PORT=5177` |

Before the fix `wire_prek` created `prek.toml` unconditionally. prek's lookup order was measured
directly in one-shot repositories for every pair: `prek.toml` beats `.pre-commit-config.yaml`
beats `.pre-commit-config.yml`, and prek names the loser
(`warning: Multiple configuration files found (…); using …`). So the created `prek.toml` outranked
the file the project actually used, and `lint-canary` would have stopped running. `prek_config_path`
now mirrors that order. The same probes confirm real `pre-commit` reads **only**
`.pre-commit-config.yaml` — with just a `.yml` present it fails with
`InvalidConfigError: .pre-commit-config.yaml is not a file` — so the pre-commit adapter still
writes that one spelling.
